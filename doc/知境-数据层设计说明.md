数据访问与界面、模型推理解耦，落实说明书 7.2「数据入口、内容理解、检索、界面展示分开」。

├── DbConstants.kt              # 全局常量
├── entity/                     # 20 个 Room 实体（internal）
├── dao/                        # 对应 DAO（internal）
├── repository/                 # 13 个 Repository 接口 + 实现
├── model/                      # 对外领域模型与枚举（public）
│   ├── Enums.kt                #   业务枚举（状态/来源/类型）
│   ├── ContentModels.kt        #   Content / Chunk / ChunkPayload / RetrievedContent
│   ├── RelationModels.kt       #   Association / Topic / StanceCompare
│   ├── ActivityModels.kt       #   WakePlan / QaRecord / PetStatus / ParseTask
│   ├── KgModels.kt             #   ProbeStatus / ClaimSource / ClaimReviewStatus / RuntimeClaim / ClaimProbeState / ClaimMerge
│   └── GeneratedGraphModels.kt #   GeneratedGraph / GeneratedOutlineNode / GeneratedCard / GeneratedPrerequisite

## 3 分层架构

```
:app（Compose UI / 会话编排 / RAG 索引 / 云端客户端 / 图谱引擎）
   │
   ▼
ZhiJingData（对外唯一入口，public）
   │
   ├── conversations  contents  associations  topics  stanceCompares  wakePlans
   ├── qaRecords      petStatus  parseTasks
   └── kgStates       kgClaims  kgGenerated
   │
   ▼
DAO 层（internal，suspend + Flow）
   │
   ▼
Entity 层（internal，20 张表）
   │
   ▼
Room / SQLite（zhijing.db，应用私有目录）
```

约定：

- 模块外只能看见 `ZhiJingData`、13 个 Repository 接口、`model` 包中的领域模型与枚举、`DbConstants`。
- Room 实体、DAO、`ZhijingDatabase`、TypeConverter、向量数学全部 `internal`，调用方接触不到 BLOB 与 SQL。
- 上层**不得**自建 Room 数据库或直接写 SQL；写向量统一走 `contents.updateEmbedding`，检索统一走
  `contents.searchSimilar`。

## 4 数据库设计

### 4.1 总览

Room，文件 `zhijing.db`，`version = 7`，`exportSchema = false`，共 **20 张表**，分四组：

| 分组 | 表 | 设计理由 |
| --- | --- | --- |
| 说明书 3.4 规定（8） | `content_table`、`association_table`、`topic_table`、`stance_compare_table`、`wake_plan_table`、`qa_record_table`、`pet_status_table`、`parse_task_table` | 字段名与说明书逐字对齐，便于验收与队员对齐 |
| RAG 扩展（2） | `chunk_table`、`vector_table` | 说明书只有整篇 `raw_text`（最长 5000 字），整篇转向量粒度太粗；分段 + 段级向量支撑「回答里引用原文片段」 |
| 多会话与记忆（2） | `conversation_table`、`message_table` | 说明书 3.4.6 的 `qa_record_table` 没有 `conversation_id` / `seq` / `token_count`，无法做多会话与上下文预算 |
| 知识图谱运行时（8） | `kg_claim_state`、`kg_condition_probe`、`kg_runtime_claim`、`kg_claim_merge`、`kg_generated_graph`、`kg_generated_outline`、`kg_generated_card`、`kg_generated_prerequisite` | 出厂图谱是出版物（`assets/kg/graph.json`），不进库；进库的只有运行期产生的状态、增量命题与按主题生成的图谱 |

### 4.2 三个关键设计决策

**（1）出厂图谱不进数据库。** `assets/kg/graph.json` 是只读出版物（outline / card / claim / edge）。
如果也写进 Room，就出现「两份真相」和迁移负担，而离线可读性由 assets 已经保证。因此库内只存：
判断状态（`kg_claim_state`）、条件级探测记录（`kg_condition_probe`）、云端/用户增量命题
（`kg_runtime_claim`）、ID 合并映射（`kg_claim_merge`）、用户生成的图谱（`kg_generated_*`）。
渲染时由 `GraphAssembler` 合并。

**（2）命题 ID 漂移用「重定向表」解决。** 命题 ID 由 `sha1(规范化 statement)[:4]` 推导
（`kg/schema/id-spec.md`）。出厂命题 ID 固定；但云端每次生成的措辞略有不同，ID 就会变，而判断状态
挂在旧 ID 上，同一命题会出现两条、状态丢失。`kg_claim_merge` 把派生 ID 映射到规范 ID，所有读写先过
这张表（`kgClaims.resolveClaimIds(...)`），等价于给 ID 加了一层稳定重定向。

**（3）向量双写但只有一个真源。** 说明书 3.4.1 要求 `content_table.embedding_vector` 列存在，
同时又要求「支持按内容增删改」。因此 `vector_table` 作为唯一真源统一承载内容级与分段级向量，
写入内容级向量时在同一事务内同步刷新 `content_table.embedding_vector`，两者不会漂移。

### 4.3 表清单

逐列定义见 [`docs/数据库结构.md`](../docs/数据库结构.md)。需要记住的约束：

| 表 | 关键约束 |
| --- | --- |
| `content_table` | 原文超 5000 字由数据层截断；`analysis_status` / `embedding_status` 为说明书规定的 INTEGER 码 |
| `chunk_table` | `content_id` 外键 CASCADE；`(content_id, chunk_index)` 唯一，段序号由数据层按传入顺序分配 |
| `vector_table` | `(owner_type, owner_id)` 唯一；**无外键**（owner 多态），删除必须显式清理 |
| `conversation_table` | `digest` + `digest_up_to_seq` 记录「摘要覆盖到第几条消息」，恢复会话时不必重算 |
| `message_table` | `conversation_id` 外键 CASCADE；`(conversation_id, seq)` 唯一；`seq` 由 `appendMessage` 统一分配 |
| `association_table` | 两端均 CASCADE；反馈权重累加依据 `AssociationFeedback.weightDelta` |
| `topic_table` | 主题名是主键，自引用 `parent_tag` 构成树 |
| `pet_status_table` | 单例，主键恒为 1（说明书未给主键，数据层补充） |
| `parse_task_table` | `content_id` 外键 CASCADE；重试上限 3 次（`DbConstants.MAX_PARSE_RETRY`） |
| `kg_claim_state` | 主键即命题 ID，与 assets 中的 `clm.*` 对齐；**无外键**，孤儿状态由 `pruneOrphans` 清理 |
| `kg_condition_probe` | 主键 `(triple_id, intervention_id)`，与 assets 的 `triples` 对齐；只记条件粒度，命题级收敛仍走 `kg_claim_state` |
| `kg_runtime_claim` | 主键 `claim_id`；`pending` 不进入任何视图，确认后才进图谱 |
| `kg_claim_merge` | 主键 `source_claim_id`，一条源 ID 只能指向一个目标，避免链式映射 |
| `kg_generated_graph` | 主键 `topic_id`；同一主题重复生成整份覆盖，不保留历史版本 |
| `kg_generated_outline` / `_card` / `_prerequisite` | 复合主键含 `topic_id`；三者在同一事务内整份替换 |

### 4.4 枚举与转换器

- 业务枚举（`AnalysisStatus`、`EmbeddingStatus`、`ParseTaskStatus`、`AssociationFeedback`、`StanceStatus`、
  `AnswerStatus`、`PetPhase`、`ImportChannel`、`WakeMode`、`ParseTaskType`、`VectorOwnerType`）由
  `EnumConverters` 转成说明书要求的 INTEGER / TEXT。**不要**依赖 Room 默认的「枚举名存 TEXT」。
- 知识图谱的三个枚举（`ProbeStatus`、`ClaimSource`、`ClaimReviewStatus`）在实体里就是 wire 字符串，
  由 `KgEntityMappers` 在映射时转换，不经过 TypeConverter。
- 列表分两套：`ListConverters`（ID 列表 ⇄ 逗号分隔）、`StringListConverters`（短句列表 ⇄ JSON 数组）。
  短句里可能出现逗号、顿号，**不能**为了统一而改用逗号拼接。

### 4.5 外键与级联

| 子表.列 | 父表 | 行为 |
| --- | --- | --- |
| `chunk_table.content_id` | `content_table.id` | CASCADE |
| `parse_task_table.content_id` | `content_table.id` | CASCADE |
| `association_table.source_content_id` / `target_content_id` | `content_table.id` | CASCADE |
| `message_table.conversation_id` | `conversation_table.id` | CASCADE |

`vector_table` 与全部 `kg_*` 表**没有外键**（owner 多态 / 命题在 assets 里），必须由 Repository 或
维护任务显式清理。这是最容易遗漏的地方。

## 5 向量存储与相似度检索

### 5.1 存储格式

- 维度固定 512（说明书 6.2、内置参数 `vector_dim`）。
- 小端 float32 × 512 = **2048 字节**，由 `VectorCodec` 编解码。
- `decode` 对 null 或长度不为 2048 的输入返回 null 而不抛异常，单条坏向量只被跳过。
- `vector_table.model_id` 记录产出向量的模型；换嵌入模型后可据此判定旧向量失效。

### 5.2 检索方式

```
vector_table（按 owner_type 整表取回）
      │  VectorCodec.decode（过滤坏数据）
      ▼
候选 (ownerId, FloatArray)
      │  CosineSimilarity.topK(query, candidates, topK, threshold)
      ▼
降序 + 阈值过滤 + 截断 topK
      │  回查 content_table / chunk_table
      ▼
List<RetrievedContent>
```

选型理由：零原生依赖、实现简单、便于演示。N=500 时约 500×512 次乘加，配合一次整表 BLOB 读取，远低于
说明书 5.1「问答检索一秒以内」，因此**未做内存向量缓存**（避免缓存失效带来的一致性问题）。

扩展点：检索抽象为 `VectorSearchStore`，默认实现 `RoomVectorSearchStore`。将来换 sqlite-vec 只需替换
该实现，Repository 与上层无需改动。

### 5.3 召回规则

- 余弦相似度：长度不一致、任一为空或模长为 0 时返回 `0.0`，不发生除零。
- 默认阈值 `0.65`、默认 Top-K `5`（说明书内置参数）。
- `searchSimilar(..., includeChunks = true)` 在分段级向量上检索，命中结果带 `matchedChunkIndex` 与
  `matchedText`，供回答引用原文片段。

### 5.4 端云约束

**检索与嵌入永远在端侧完成**，即使回答由云端生成。云端只参与文本生成，不接触用户内容向量。

## 7 数据一致性与事务边界

说明书 5.2 要求「本地数据读写正确率 100%，内容、标签、向量、关联之间保持一致」。

| 事务 | 涉及表 | 保证 |
| --- | --- | --- |
| `saveImportedContent` | content + chunk + parse_task | 内容、分段、两个解析任务同写同不写 |
| `updateEmbedding`（有新向量） | vector + content | 真源与镜像列双写一致 |
| `deleteContent` | content + chunk + vector + association + parse_task | 内容及派生数据一并清除 |
| `deleteAllContents` | 上述 + stance_compare | 清空收藏并清掉观点对照（说明书 4.2.5） |
| `appendMessage` | message + conversation | 分配 `seq` 的同时刷新会话 `updated_at` |
| `submitFeedback` | association | 读旧权重、累加增量、写回，避免并发丢更新 |
| `markFailed` | parse_task | 累加重试次数，按是否达上限决定重排或置失败 |
| `GeneratedGraphRepository.save` | kg_generated_*（4 张） | 同一 `topic_id` 整份替换 |

要点：

- **`vector_table` 无外键**，删除内容/清空时必须显式删向量；其余子表另有外键级联作双保险。
- **向量化失败不丢数据**：`updateEmbedding(vector = null, status = FAILED)` 只改状态、保留旧向量。
- **空原文不入库**：`saveImportedContent` 对空白原文抛 `IllegalArgumentException`（说明书 4.2.1）。
- **原文截断**：超过 5000 字由数据层截断（说明书 3.3.1）。
- **`pruneOrphans` 的保护**：传入空列表时直接返回 0，不执行删除——「现在什么都没有」多半是调用方
  加载失败，不能误删全部状态。
- **`addCandidate` 用 IGNORE**：同一条命题被云端重复生成时保留既有记录与审核状态，不覆盖。

## 10 与其他模块的对接约定

| 模块 | 使用方式 |
| --- | --- |
| 会话与记忆 | `conversations.createConversation` / `appendMessage`（**必须使用返回的 seq**）/ `messagesAfter` / `updateDigest` |
| RAG 索引 | `contents.saveImportedContent(...)` → 逐段 `engine.embed` → `contents.updateEmbedding(...)`（由 `RagIndexer` 驱动） |
| 问答检索 | `contents.searchSimilar(..., includeChunks = true)`，**始终端侧执行**；结果拼进提示词 |
| 问答记录 | `qaRecords.save(...)` 记录问题、回答、引用内容 ID 与耗时 |
| 关联推荐 | `associations.save(...)`；反馈用 `associations.submitFeedback(...)` 更新权重 |
| 认知庭院 | `topics` 读主题树；`petStatus` 读写动物状态 |
| 观点对照 | `stanceCompares` 读写对照组 |
| 记忆唤醒 | `wakePlans.getEnabled()` 取计划，执行后 `updateSchedule(...)` |
| 知识图谱-广度侧 | `kgClaims.observeConfirmed()` + `kgGenerated.allOutline/allCards/allPrerequisites` + `kgStates.observeAllStates()`，由 `GraphAssembler` 合并 |
| 知识图谱-深度侧 | `kgStates.recordJudgement(...)` 回写判断；`kgClaims.addCandidate(...)` 写候选；审核用 `review(...)` |
| 界面层 | 只经 Repository 读写；列表数据优先用 `observeXxx()` 的 Flow 驱动 Compose |

**禁止事项**：不得直接引用 `entity` / `dao` / `ZhijingDatabase` / `VectorCodec`（均为 `internal`，
编译期即被拦截），不得自建 Room 数据库，不得自行写 `vector_table`。

## 11 已知取舍与遗留

| 项 | 现状 | 说明 |
| --- | --- | --- |
| **数据库迁移** | ⚠️ `fallbackToDestructiveMigration()` 已开启 | 任何 `version` 变更找不到 Migration 就会**清空全部用户数据**。开发期可接受；有真实数据前必须补 `Migration` 并移除该调用 |
| 实体关系表 | 未单独建表 | 说明书无此表：实体存于 `content_table.analysis_json`，内容间关系在 `association_table`，主题层级在 `topic_table`；知识图谱的实体/关系由 assets 图谱 + `kg_runtime_claim` 表达 |
| 内存向量缓存 | 未实现 | 当前数据量下解码开销远低于 1 秒预算；保留 `VectorSearchStore` 接口以便将来接入 |
| 一键清空 / 日志导出 | 未实现 | 说明书 6.3 / 7.3 要求；`deleteAllContents()` 与各 Repository 的 `deleteAll()` 已可作为底层能力 |
| `analysis_json` 解析 | 原样存 TEXT | 未引入 JSON 库，解析职责归内容理解模块 |
| ID 列表存储 | 英文逗号分隔 | 仅用于纯数字 ID，无分隔符歧义；短句列表已改用 JSON（`StringListConverters`） |
| 出厂图谱与运行时数据 | 分两处存放 | 出厂在 assets（只读），运行时在 Room（可写）；改动时注意不要引入「两份真相」 |
| 孤儿清理 | 半自动 | `kg_claim_state` / `kg_condition_probe` 无外键，命题或三元组下架后需调用 `pruneOrphans(...)`（两者空列表都不清空）；`vector_table` 同理 |
| 条件级状态 | 独立一张表 | 「掌握没有」（`kg_claim_state`）与「错在哪条机制」（`kg_condition_probe`）是两个粒度，合表会丢机制；一次「预测 → 揭示」只写条件级，避免同一道题算两次 |
