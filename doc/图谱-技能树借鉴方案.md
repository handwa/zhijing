# 图谱改进方案：借鉴 cs-math-skill-tree

> 参考：GitHub [zeroa234/cs-math-skill-tree](https://github.com/zeroa234/cs-math-skill-tree)（MIT，纯静态网页，离线可用）。
> 本方案只讨论"图谱这一部分"能借鉴什么，落到知境现有代码结构上。

## 一、参考项目是什么

把计算机专业 + 数学做成可逐步"点亮"的技能树：13 个领域、193 个技能、262 条必须前置 + 403 条推荐前置。核心体验由四件事支撑：

1. **节点三态状态机**：已点亮 / 现在能学（所有必须前置已满足）/ 未解锁，颜色之外还有图标（照顾色弱）。
2. **"现在能学"队列**：按"学完能解锁多少后续技能"贪心排序，用户永远知道下一步点哪个。
3. **分层布局 + 前置链高亮**：步骤 = 最长必须前置链长度（全树 7 步），领域泳道左→右；选中节点后实线 = 必须前置链、虚线 = 推荐前置、绿线 = 直接解锁的后续。
4. **进度持久化 + 导出/导入**：进度存在本地，可导出 JSON；技能合并时旧记录保守保留。

技术栈是 elkjs（构建时算分层布局）+ panzoom + markmap/d3（只渲染知识导览图），数据是构建期从源数据校验合并出的静态 JSON（构建脚本拒绝无证据的连线、有环即失败）。

## 二、知境图谱现状对照

| 能力 | cs-math-skill-tree | 知境现状 | 差距 |
|---|---|---|---|
| 节点级状态机 | 已点亮/现在能学/未解锁 | 只有命题四态（`ProbeStatus: CONFUSED/UNPROBED/VERIFIED/MASTERED`，`kg_claim_state`），无卡片级"已学/可学" | **缺** |
| "现在能学"队列 | 贪心按解锁后续数排序 | 无任何"下一步学什么"逻辑 | **缺** |
| 前置链驱动交互 | 实/虚/绿三线高亮 + 解锁门控 | `prerequisites` 已有 `required/recommended`，但只做实/虚线**视觉区分**，不门控、不驱动推荐 | 半成品 |
| 分层布局 | elkjs 分层布局 | Compose Canvas 横向 tidy tree（`TreeLayout.kt`），明确否决力导向 | **已达标，无需借鉴** |
| 缩放/平移 | panzoom | `GraphTreeView` 自带 pan/zoom + 自适应 | 已达标 |
| 前置关系数据 | 必须前置 + 推荐前置 + 证据 | `prerequisites`（required/recommended + reason/source）+ claim 级 `edges` | 数据已齐 |
| 进度持久化 | localStorage + 导出/导入 | Room 探测表，无导出 | 小差距 |
| 学习资源（去哪学） | 每技能中英资源、逐章节映射 | 卡片有 `summary/body`，无资源字段 | 可选 |
| 选中高亮样式 | 三种线型 + 跨领域彩点 | 已有实/虚/CROSS 三种线 | 基本达标 |

**关键结论**：知境的前置链**数据**已经齐全（`graph.json` 的 `prerequisites`、生成图谱的 `kg_generated_prerequisite`），缺的只是把它们变成**驱动学习行为的引擎**——状态机、队列、门控。这是一层纯派生逻辑，不需要改数据模型。

## 三、虚实线语义对照：两边一样吗？

**结论：主语义一致，但知境的"实线/虚线"各有两重含义，参考项目每种线型只承担一种语义。**

### 3.1 逐项对照

| 视觉 | cs-math-skill-tree | 知境（`TreeLayout.kt` L122–129 视觉契约 + `GraphTreeView.kt` 渲染） | 一致？ |
|---|---|---|---|
| 实线 | **仅一种含义**：必须前置链 | 有**两种**实线：`PREREQUISITE_REQUIRED`（`#D63031` 暗红实线 + 箭头，3dp）和 `HIERARCHY`（章节→子节点，淡实线） | ⚠️ 部分 |
| 虚线 | **仅一种含义**：推荐前置（只提示不挡路） | 有**两种**虚线：`PREREQUISITE_RECOMMENDED`（`#F39C12` 暖橙虚线、**无箭头**，2dp）和 `CROSS`（交叉链接，细虚线 1dp、无箭头、最淡） | ⚠️ 部分 |
| 绿线 | 直接解锁的后续技能 | **已实现为"后续线"**：选中卡片时从它出发的依赖边，`#0984E3` 柔和蓝实线 + 箭头（颜色不用绿，避免与层级线/主色混淆） | ✅（色不同） |
| 跨领域标识 | 领域总览线粗 = 跨领域必须前置条数；卡片彩点 | 知境无"跨领域"维度（单一主题树） | 不适用 |

### 3.2 一致的部分（不用改）

**必须前置=实线、推荐前置=虚线**这一核心编码两边完全一致：知境的 `PrerequisiteKind.REQUIRED→实线 / RECOMMENDED→虚线` 映射（`TreeLayout.kt` 前置边生成处）与参考项目语义同源，且 `graph.json` 数据层就带 `kind` 字段。**这条主链路无需任何改动。**

**2026-11-15 起的显示规则**：未选中任何卡片时只画层级线，依赖线一律不画；选中后只画与它相连的线，并按方向换称谓——指向选中卡的是「前置」，从选中卡出发的是「后续」（`EdgePresentation.roleOf`）。所以上面说的"实线二义性"在实际屏幕上被选中态隔开了，只有选中时才会同时出现。

### 3.3 不一致的部分

1. **知境"虚线"的二义性**：`CROSS`（卡片间词共现交叉链接）也用虚线，靠"更细、无箭头、颜色更淡"与推荐前置区分。参考项目每种语义严格一种线型；对色弱用户，两条黄色系虚线可能混淆。
2. **知境"实线"的二义性**：`HIERARCHY`（大纲层级连线）也是实线，靠"最淡"区分。参考项目没有层级连线（它的层级由泳道位置表达，不画线）。
3. **后续线已补上，但"实线"又多承担了一层语义**：选中卡片后，`from` 端出发的依赖边统一画成蓝色实线 + 箭头（用户定的「后续线」）。副作用是：一条**推荐**前置被反向看时，会从"暖橙虚线"变成"蓝色实线"，与"实线只表示必须"的冻结约定冲突。这是有意为之（方向比强弱更重要），但写在这里以免以后被当成 bug 改回去。

### 3.4 如果要改：改动量与产品影响评估

**总体评级：低风险、纯视觉层改动，数据层与业务逻辑零改动。**

| 改法 | 触及的代码 | 对现有产品的影响 |
|---|---|---|
| **方案 A：保留现状（推荐）** | 无 | 主语义两边一致，二义性靠宽度/箭头/透明度已可区分；不改用户任何已有习惯 |
| **方案 B：消歧 CROSS**——交叉链接改灰色点线（点更小更密），与推荐前置的"短横虚线"拉开 | `GraphTreeView.kt` 渲染分支 ~L540–555（一处 `PathEffect`） | 仅交叉链接的外观变化；`crossLinks` 数据、点击行为、布局全不动。用户感知：连线更像"弱关联"，反而更符合语义。影响面 ≈ 一个 drawLine 分支 |
| **方案 C：消歧 HIERARCHY**——层级连线改点线；或干脆不画（参考项目做法：层级靠布局表达） | `GraphTreeView.kt` HIERARCHY 分支；若"不画"则 `TreeLayout` 生成 HIERARCHY line 时跳过 | "不画"会损失"章节→首卡"的视觉锚点，需要用户适应；改点线几乎无感知。建议改点线、不采纳"不画" |
| **方案 D：新增绿线（解锁后续）**——服务 P1 的"选中链路高亮" | `TreeLayout.Line.Style` 加一个枚举值 + `GraphTreeView` 加一个渲染分支 + 选中时取子孙一层（`TreeLayout` 已有树结构，可直接取 children） | **新增能力，不覆盖任何现有视觉**；唯一注意点是绿色别与 CROSS/HIERARCHY 的灰色系混淆。影响面 = 一个枚举值 + 两个渲染/计算分支 |
| **不可行的改法**：把实线含义改成"选中链路专用" | 需重构 `Line.Style` 语义并重画全图 | **不建议**——会推翻"实线=必须前置"这个两边一致、用户已建立心智的核心编码 |

**共同的连带成本**：`:app` 单测中涉及 `TreeLayout`/线型映射的期望值需同步（新增枚举值时）；`kg/tests`（Python）不触及渲染层，无需改动。`graph.json`、`kg_generated_prerequisite`、Room 各表全部不动。

**建议**：采用 A + D——虚实线主语义不动（本来就一致），在 P1 做"选中链路高亮"时顺手加绿线；B/C 作为无障碍打磨放在 P2 之后可选。

## 四、落地方案（按优先级）

### P0：卡片三态状态机 + "现在能学"侧栏（核心，纯派生层）

1. **新增 `SkillProgress.kt`**（`app/.../kg/`，纯 Kotlin 无 Android 依赖，配套单元测试）：
   - 输入 `MergedGraph`（GraphAssembler.merge 的产物）+ `kgStates` 的命题状态。
   - **卡片级掌握度**：把 `kg_claim_state` 的四态按 `claim.breadth` 聚合到卡片 → 规则建议：卡内 ≥80% 命题 MASTERED 且 VERIFIED≥1 判"已点亮"；存在 VERIFIED/MASTERED 即"进行中"。
   - **三态判定**：`LIT`（已点亮）/ `READY`（所有 required 前置卡片已点亮，且自身非 LIT）/ `LOCKED`（存在未点亮的 required 前置）。
   - **后续计数**：`downstreamCount(cardId)` = 直接和间接解锁的卡片数（对应参考项目的"后续 44"），用于排序。
   - recommended 前置**不参与**判定，与参考项目语义一致（"只提示，不挡路"）。
2. **GraphScreen 左侧/底部加"现在能学"面板**：列出 READY 卡片，按 downstreamCount 降序；每项显示"后续 N"。点击即定位（复用现有 `GraphFocus`）。
3. **顶部进度条**："x / y 已点亮"，x=已点亮卡片数，y=卡片总数。
4. **状态图标**：三态在颜色之外加图标（✓ / ⊕ / 🔒），沿用参考项目的无障碍考虑。

不改 Room：三态全部实时派生，与现有"状态不进图谱数据、只派生"的架构约定一致（GraphAssembler 已有 badgeStatus 先例）。

### P1：选中节点的前置链路强化 + "下一步"推荐

1. **选中高亮升级**（`GraphTreeView.kt`）：点选卡片时——
   - 实线高亮整条 required 前置链（祖先闭包）；
   - **绿色高亮直接解锁的后续（子孙一层）**，即 3.4 的方案 D；
   - 未在链路上的边降透明度。
   现有三种线型样式可复用，只需加"按选中节点过滤"的逻辑。
2. **设为目标模式**：长按/菜单把某卡片设为"目标"→ 状态机反推需要点亮的卡片集合，生成按拓扑序编号的学习清单（对应参考项目的"设为目标后左栏生成编号清单"）。可先做内存态，不落库。
3. **点亮动效**：卡片从 READY→LIT 时在树视图上做一次涟漪/描边动画（Canvas 上加 animateFloatAsState 即可），强化"点亮"的游戏感。

### P2：进度导出/导入 + 生成图谱解锁打通

1. **进度导出**：把 `kg_claim_state` / `kg_condition_probe` 序列化为 JSON，从设置页导出/导入（参考项目的 localStorage 导出）。这一步也顺带规避了 Room `fallbackToDestructiveMigration` 升级清库丢进度的风险。
2. **生成图谱接入同一状态机**：`kg_generated_prerequisite` 的 required 边同样参与三态判定，让用户自建图谱（GRAPH_GENERATE）也获得"可学/解锁"体验——`SkillProgress` 输入是 `MergedGraph`，天然覆盖生成树，只需确认生成前置边在 merge 后语义一致。
3. **学习资源字段**（可选，改动最大）：卡片详情加"去哪学"条目（链接列表）。若做，来源可以是用户在详情页手工添加存 Room，或导入文档时由模型抽取；不推荐照搬参考项目的 388 条人工核对资源——成本不成比例。
4. **线型无障碍打磨**（可选）：3.4 的方案 B/C——交叉链接改点线、层级连线改点线，消除虚线/实线的二义性。

### 明确不借鉴的部分

- **elkjs / d3 / markmap**：知境是 Compose Canvas 自绘 tidy tree，布局已稳定且刻意否决了力导向；引入 WebView 或 JS 引擎得不偿失。
- **URL hash 路由**：知境是单 Activity 枚举导航 + 对话框下钻，不需要。
- **CS2023 课程标准对齐 / 主干选修划分**：那是参考项目对"全学科"的编辑性工作，知境图谱来自用户自己的文档，范畴不同。
- **无证据连线的构建期校验**：知境已有等价物（`PrerequisiteValidator.validate()` 去环、`ClaimIngestor` 确认门控），无需再加。
- **推翻现有实/虚线语义**：两边主语义一致（实=必须、虚=推荐），没有任何理由为此重构渲染层。

## 六、风险与约定

- **门控不做"写死"**：三态只是派生展示 + 建议顺序，不阻止用户点击 LOCKED 卡片查看内容（参考项目详情面板本身也开放）。避免把学习工具变成强制关卡。
- **掌握度阈值**放常量便于调参；首版用简单规则（80% MASTERED），后续可换成基于探测正确率的加权。
- 生成图谱的 required 边质量参差（`OutlineBuilder` 是兜底生成的），其三态判定可以只对出厂图谱启用，生成图谱第一版只显示计数不门控。
- `GraphModeStore`（OFFLINE/CLOUD_ENHANCED）与该状态机无关，不要耦合；状态机在两种模式下都工作（数据都在本地 Room）。
- **线型语义冻结**：实线=必须前置、虚线=推荐前置这条编码保持不变；后续任何新语义（如绿线）只能用**新增**线型/颜色表达，不得复用现有实/虚线。
