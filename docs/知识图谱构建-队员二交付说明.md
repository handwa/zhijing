## 2. 设计判断：为什么是「两张图」而不是「一张节点图」

设计文档的核心结论是：**广度图谱回答「由哪些部分组成」，深度图谱回答「这个点到底成不成立」；两者不是同一种工作的放大缩小。**

落到实现上，有三处必须做对，否则项目会退化成「加了测试的思维导图」：

1. **一个命题只有一条记录、两个渲染面。** `breadth` 给阅读，`depth` 给判断。两边各存一份，迟早不一致。
2. **边必须带条件。** 边不是连线，是「依赖与影响」；条件是「适用范围」。写不出边界的边没有存在价值，校验器会直接判失败。
3. **深度只能下钻。** 没有独立入口、独立目录、独立 URL。一旦并列，叶子卡片的主归属就失去意义。

与说明书的关系：说明书 6.1.2 把「认知庭院」描述为「节点是内容、连线是关联」的主题树，那是**广度侧 + 结构图**；设计文档补齐了说明书没写的那一半——**判断层**。两者是同一套数据的两种尺度。

## 3. 实体与关系抽取

### 3.1 实体（6 类）

| kind | 含义 | 例子 | 判定信号 |
|---|---|---|---|
| `concept` | 概念 | 梯度消失、残差连接、因果掩码 | 加粗 + 定义句式「X 是…」 |
| `method` | 方法 / 层 / 算子 | ReLU、LayerNorm、缩放点积注意力 | 领域词表 |
| `metric` | 指标 / 损失 | 交叉熵、MSE | 领域词表 |
| `tool` | 工具 / 框架 | PyTorch、llama.cpp | 词表 + 大写缩写 |
| `dataset` | 数据集 | ImageNet | 词表 |
| `formula` | 公式或张量记号 | logits、`(N, C)`、`sqrt(d_k)` | 行内代码 + 括号/等号 |

同一实体的多种写法（`ReLU` / `线性整流`、`CrossEntropy` / `交叉熵`）归并到 `canonicalName`，其余进 `aliases`；`mentions` 记录它出现在哪张卡的原文哪个写法上——这是「实体 → 卡片」的反向索引，用于生成交叉链接。

### 3.2 关系（6 类）

| type | 语义 | 什么时候用 |
|---|---|---|
| `depends_on` | 依赖：下游成立需要上游成立 | 「A 的前提是 B」 |
| `affects` | 影响：上游变化改变下游结果 | 「A 出问题会让 B 失真」 |
| `contains` | 组成：整体由部分构成 | 「多头注意力包含 Q/K/V 投影」 |
| `contrasts` | 对比：易混，需并置区分 | 「LayerNorm 与 BatchNorm 差别在归一化维度」 |
| `refutes` | 反例：存在使其不成立的场景 | 「ReLU→Softmax 是『形状对就语义对』的反例」 |
| `prerequisite` | 前置：学习顺序 | 「先懂形状依赖，再谈残差形状约束」 |

### 3.3 条件（5 类，撞错时用来定位错点）

`shape` 形状依赖 / `range` 值域依赖 / `statistics` 统计量依赖 / `gradient` 梯度路径依赖 / `semantic` 语义依赖。

这是整套设计里最实用的一处：用户判错后，系统不是只说「你错了」，而是说「错在语义依赖——形状对得上，但 Softmax 要的是未归一化 logits」。演示页的「错点落在哪条依赖上」就是这张表在渲染。

### 3.4 抽取方式：规则为主，LLM 为辅

| Markdown 结构 | 抽取产物 | 实现 |
|---|---|---|
| `#` / `##` / `###` 标题 | 大纲节点（层级树） | `parse_markdown.py` |
| 段落 / 列表 / 表格 / 代码块 | 卡片（可独立阅读的单元） | `parse_markdown.py` |
| 领域词表 / 加粗 / 行内代码 | 实体 + 出现位置 | `extract_rules.py` |
| 判断题表（判断句｜是否成立｜边界） | 命题（含 `expected`） | `extract_rules.py` |
| 代码块 `A → B → C` | 卡片的 `chain`（组成关系） | `extract_rules.py` |
| ```yaml kg:claim``` 标注块 | 命题 + 带条件边 | `parse_markdown.py` + `build_graph.py` |

为什么规则为主：**可复现、可 diff、零幻觉**。为什么仍然保留 LLM：规则只认识词表里的词，开放词表与运行时扩充必须靠模型。

两者写入同一格式（`prompts/output_contract.md` 给了逐字段对应表），所以「人工精标」和「模型回填」不会变成两套数据。LLM 的硬约束只有一条：**实体名与 evidence 必须逐字回查原文，回查不到直接丢弃**——不靠模型自觉。

提示词针对端侧小模型做了取舍：一次只做一件事、temperature 0.1、输出 ≤512 token、强制带一条 few-shot、明确允许返回空结果（宁缺毋滥）。

## 4. 节点与边设计

### 4.1 四类节点

| 类型 | ID 前缀 | 能不能下钻 | 关键字段 |
|---|---|---|---|
| `outline` 分类节点 | `out.` | **不能**（`descendable: false`） | 层级、父节点、路径 |
| `card` 卡片 | `crd.` | 叶子卡片能 | 摘要、正文、交叉链接、`claimIds` |
| `claim` 命题 | `clm.` | — | `statement`、`conditions`、`breadth`、`depth` |
| `entity` 实体 | `ent.` | — | kind、标准名、别名、出现位置 |

### 4.2 命题的双视图契约

```json
{
  "id": "clm.arch.dep.relu-then-softmax.7f3a",
  "statement": "ReLU 之后可以直接接 Softmax 输出类别概率。",
  "conditions": ["形状依赖满足…", "语义依赖不满足…", "边界：C=1 时恒输出 1"],
  "evidence": "形状完全相容，可 ReLU 的输出不是 logits。",
  "breadth": { "outlinePath": "s2-5", "cardId": "crd.s2-5",
               "cardSummary": "…", "leafContent": "…" },
  "depth": {
    "edges": ["edg.dep.1a2b3c", "edg.ref.4d5e6f"],
    "judgementPanel": {
      "question": "这个说法成立吗？",
      "expected": false,
      "reveal": { "explanation": "…", "errorKinds": [{"kind": "semantic", "why": "…"}],
                  "misconception": "…" }
    },
    "probeState": { "probe_status": "confused", "last_probed_at": null,
                    "misconceptions": ["…"], "confidence": 0.3 }
  }
}
```

`breadth` 的字段是**白名单**（`outlinePath / cardId / cardSummary / leafContent`），校验器会拦下任何多余字段——这是「条件不能在第一屏铺开」在数据层的强制手段。

### 4.3 ID 规范

`<前缀>.<语义路径>.<稳定短哈希>`，哈希取 `sha1(规范化 statement)[:4]`：改标点不改 ID，改实词换 ID。

| 类型 | 示例 |
|---|---|
| 大纲 | `out.s1-1-linear` |
| 卡片 | `crd.s1-1-linear` |
| 命题 | `clm.arch.ffn.linear-in-dim.4a3e` |
| 实体 | `ent.method.relu.5f21` |
| 边 | `edg.dep.14d21a`（类型短码 + 端点+类型哈希） |

「ID 当发布物对待」不是口号：`build_graph.py` 每次构建都会和上一版 `graph.json` 比对，把**新增 / 消失的命题 ID** 写进 `meta.warnings`，改名会立刻暴露。

### 4.4 交叉链接：封顶 5 条并按权重排序

权重 = 共享实体数 / √(两卡实体数之积)，同章再加 0.03。取前 5 条。
这一步看着小，实际是「阅读容器」和「节点图」的分水岭：不封顶，每张卡都会连出十几条边，用户立刻失去定位感。

## 5. 导入脚本

```bash
python kg/src/build_graph.py      # 语料 → kg/data/out/graph.json
python kg/src/validate_graph.py   # 8 条约束校验，失败非 0 退出
python kg/src/export.py --all     # web 数据 + Android assets + SQLite 种子
```

| 脚本 | 职责 | 可单独运行 |
|---|---|---|
| `kg_model.py` | 枚举 / ID / 哈希 / 标注块解析（唯一实现，自检 `python kg/src/kg_model.py`） | ✓ |
| `parse_markdown.py` | 切块、建大纲、收集标注块 | ✓ |
| `extract_rules.py` | 实体、判断题、组件链 | ✓ |
| `build_graph.py` | 组装双视图、主归属、交叉链接、边解析、导航树 | ✓ |
| `validate_graph.py` | 校验并输出人类可读报告 | ✓ |
| `export.py` | 三种导出 + `--stats` 分布统计 | ✓ |

导入产物：

| 目标 | 路径 | 说明 |
|---|---|---|
| web | `kg/web/graph-data.js` | `window.KG=…`，避开 `file://` 的 fetch 限制 |
| assets | `app/src/main/assets/kg/graph.json` | 运行时只读加载 |
| sql | `kg/data/out/graph.sql` | `kg_node` / `kg_edge` 参考表 + 种子数据 |

**刻意没做的事**：不改 `:data` 模块的 Room 实体与 `version`（队友正在改，避免冲突）。`kg_node` 主键用 TEXT 直接落命题 ID——换自增整数就等于 ID 不再是唯一真相源。

## 6. 展示格式

三屏三种动作，`kg/web/index.html` 是可运行参照，`kg/web/展示格式说明.md` 是规范。

| 屏 | 动作 | 关键约束 |
|---|---|---|
| 广度视图 | 读、查、定位 | 大纲可折叠；卡片角标四态；交叉链接 ≤5 条；叶子卡有下钻按钮 |
| 结构图 | 看关系 | 一级章节一列；实线=层级、虚线=交叉链接；可拖动缩放 |
| 深度面板 | 判、撞错 | **第一屏只有命题 + 两个按钮**；条件、反例、错点定位在作答后展开 |

状态回写闭环：

```
判错 → confused（易混淆）→ 卡片橙角标 + 易错点注记
判对 1 次 → verified（已验证）
连续判对 2 次 → mastered（已掌握）→ 卡片绿角标
```

广度侧**不存状态**：演示页用 `localStorage` 存深度侧状态、渲染时聚合；Android 端应直接按 `kg_node.probe_status` 聚合。这条对应设计文档「回写走派生，单一真相源」。

## 7. 校验与验收

`validate_graph.py` 把设计文档第五节「核心约束」逐条变成机器可查：

```
[PASS] 1. 命题 ID 全库唯一、格式合法、哈希与正文一致
[PASS] 2. 每个命题有且只有一个主归属卡
[PASS] 3. 所有边的端点都存在，无悬空边/自环
[PASS] 4. 每条边都带条件（premise + boundary + 五类 kind）
[PASS] 5. 交叉链接每卡 ≤5 条且按权重降序
[PASS] 6. 第一屏只有「命题 + 两个按钮」，条件/答案不出现在广度正文
[PASS] 7. 状态落在四态内，广度侧不存储状态（回写走派生）
[PASS] 8. 导航只有广度结构，深度图谱只能下钻
[PASS] 9. 结构完整：归属闭合、条件齐备、证据可溯源
结论：全部通过（0 项失败）
```

校验器做过**反向验证**：人为注入悬空边、缺 boundary、交叉链接超限、导航塞命题、非法状态、命题双归属，六类错误全部被对应规则拦下（不会出现「永远 PASS」的假校验）。

## 9. 已知限制与后续

| 项 | 现状 | 后续 |
|---|---|---|
| Room 落地 | 只产出 assets JSON 与种子 SQL，未建表 | 队友在 `:data` 加 `kg_node`/`kg_edge` 并配 Migration 时，直接吃 `graph.sql` |
| 运行时抽取 | 只交付提示词与契约，未接 `ParseTask` worker | 接 `InferenceEngine.sendUserPrompt`，按 `output_contract.md` 的容错链解析 |
| 语料 | 单语料（Transformer 架构） | 多语料合并需给 `build_graph.py` 加 `--source` 列表与实体跨库归并 |
| 自动命题质量 | 规则只抽「判断题表」这类强结构；其余靠精标 | 用 `extract_claims.md` 批量生成后人工 review，再落地为标注块 |
| `docs/数据库结构.md` | 仍写「10 张表、version=1」 | 实际已 12 表、version=2（含 `conversation_table`/`message_table`），建议同步更新，避免队友按旧文档改库 |

风险与缓解（沿用设计文档判断）：

- **内容成本被低估**：命题 + 条件 + 误解的产量远低于写讲解。先做垂直一小簇（本交付的 35 条），跑通闭环再扩。
- **撞错体验失败**：条件太可见 → 白点一下；太隐蔽 → 判错也看不出错在哪。本交付用「五类依赖标签」承担定位职责，条件文案要求「宽到容易判错、窄到能自己定位错点」。
- **ID 漂移**：靠 `meta.warnings` 的差异清单兜底，改名会被看见。

## 10. 五分钟演示脚本

1. 双击 `kg/web/index.html`，指出顶栏规模：22 张卡 / 35 条命题 / 16 条带条件边。
2. 点左侧「2 层与层之间的五种依赖」→ 漏斗到 5 张卡，说明**大纲只组织、不判断**。
3. 看某张卡的橙色角标「易混淆」与下方易错点注记 → 说明**广度侧角标是从深度侧聚合来的**。
4. 切「结构图」→ 拖动缩放，指出虚线是交叉链接（每卡封顶 5 条）。
5. 回到广度，点「2.5 语义依赖」卡片的「下钻 2 条命题」。
6. 第一屏只有命题与两个按钮——先让评审自己判断，再点错那个。
7. 揭示屏指出「错点落在哪条依赖上：语义依赖」，然后返回广度，看角标变橙、注记出现。
8. 收尾：`python kg/src/validate_graph.py`，说明这 8 条不是文档里的口号，是脚本每次构建都会跑的检查。
