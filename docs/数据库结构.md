# 知境 Room 数据库结构

> 来源：`data/src/main/java/com/zhijing/data/`（`:data` 模块，已纳入版本控制）
> 说明书中相关章节：3.4 数据存储
> 最近核对：2026-11-12（对应 `ZhijingDatabase` 版本 6）

## 概览

| 项目 | 值 |
|---|---|
| 模块 | `:data` |
| 数据库类 | `ZhijingDatabase`（`internal`，模块外不可见） |
| 数据库文件名 | `zhijing.db` |
| 运行时路径 | `/data/data/com.example.zhijing/databases/zhijing.db` |
| 表数量 | **19** |
| 版本 | `version = 6` |
| Schema 导出 | `exportSchema = false` |
| 迁移策略 | `fallbackToDestructiveMigration()` ⚠️ 见文末 |
| 对外入口 | `ZhiJingData.get(context)` → 12 个 Repository |
| 类型转换器 | `EnumConverters`、`ListConverters`、`StringListConverters` |

## 表分组

| 分组 | 表 | 说明 |
|---|---|---|
| 说明书 3.4 规定（8） | `content_table`、`association_table`、`topic_table`、`stance_compare_table`、`wake_plan_table`、`qa_record_table`、`pet_status_table`、`parse_task_table` | 字段与说明书逐字对齐 |
| RAG 扩展（2） | `chunk_table`、`vector_table` | 段落级检索与 512 维向量统一存储 |
| 多会话与记忆（2） | `conversation_table`、`message_table` | 归档区；`digest` / `digest_up_to_seq` 支撑上下文压缩 |
| 知识图谱运行时（7） | `kg_claim_state`、`kg_runtime_claim`、`kg_claim_merge`、`kg_generated_graph`、`kg_generated_outline`、`kg_generated_card`、`kg_generated_prerequisite` | **出厂图谱不进库**，见下 |

> **知识图谱的分工**：出厂图谱（outline / card / claim / edge）随 APK 打包在
> `app/src/main/assets/kg/graph.json`，只读，**不在 Room 中**。进库的只有运行期产生的判断状态、
> 云端/用户增量命题与同义合并映射，以及按主题生成的图谱。详见 `docs/knowledge-graph-room.md`。

对应 `ContentEntity.kt`，说明书 3.4.1。

## 3. `vector_table` 向量表

对应 `VectorEntity.kt`。说明书未定义，用于统一承载内容级与分段级向量。

| 列名 | 类型 | 说明 |
|---|---|---|
| `id` | Long | 主键，自增 |
| `owner_type` | VectorOwnerType | `content` 或 `chunk` |
| `owner_id` | Long | 对应 `content_table.id` 或 `chunk_table.id` |
| `dim` | Int | 维度，当前恒为 512 |
| `vector` | ByteArray | 小端 float 序列化后的向量（2048 字节） |
| `model_id` | String | 产出该向量的嵌入模型标识 |
| `created_time` | Long | 写入时间（毫秒时间戳） |

**索引**：`(owner_type, owner_id)` **唯一**、`owner_type`

**注意事项**：
- `vector_table` 是向量的**唯一真源**
- 写入内容级向量时，在同一事务内同步刷新 `content_table.embedding_vector`
- owner 是多态的，**无法建外键**，级联清理由 Repository 显式完成
- `model_id` 用于换嵌入模型后判定旧向量是否失效

## 4. `conversation_table` 会话表

对应 `ConversationEntity.kt`，支撑多会话与上下文压缩。

| 列名 | 类型 | 默认值 | 说明 |
|---|---|---|---|
| `id` | Long | 自增 | 主键 |
| `title` | String | — | 会话标题 |
| `system_prompt` | String | — | 本会话的系统提示词 |
| `digest` | String? | null | 被挤出上下文的旧消息提要 |
| `digest_up_to_seq` | Int | 0 | 提要覆盖到第几条消息（`message_table.seq`） |
| `created_at` | Long | — | 创建时间（毫秒时间戳） |
| `updated_at` | Long | — | 最后活跃时间（毫秒时间戳） |

**无额外索引。**

> `digest` + `digest_up_to_seq` 是「恢复会话时不必重算摘要」的关键：启动后只需读取
> `seq > digest_up_to_seq` 的消息即可补齐工作记忆。

## 5. `message_table` 消息表

对应 `MessageEntity.kt`。归档区：会话内所有消息按 `seq` 顺序保存。

| 列名 | 类型 | 说明 |
|---|---|---|
| `id` | Long | 主键，自增 |
| `conversation_id` | Long | 所属会话 |
| `role` | String | `system` / `user` / `assistant` |
| `content` | String | 消息正文 |
| `token_count` | Int | 估算 token 数，用于上下文预算 |
| `seq` | Int | 会话内序号，从 1 递增 |
| `created_at` | Long | 创建时间（毫秒时间戳） |

**外键**：`conversation_id` → `conversation_table.id`，`CASCADE`（删除会话即删消息）
**索引**：`conversation_id`、`(conversation_id, seq)` **唯一**

**并发约定**：`seq` 由 `ConversationRepository.appendMessage` 以 `maxSeq + 1` 统一分配并返回，
调用方必须使用返回值，不要自行推算，否则内存与数据库会错位。

## 13. `kg_claim_state` 命题探测状态表

对应 `KgClaimStateEntity.kt`。只存**收敛后的摘要**，逐题作答日志不进库。

| 列名 | 类型 | 默认值 | 说明 |
|---|---|---|---|
| `claim_id` | String | — | **主键**，命题 ID，如 `clm.arch.ffn.relu-shape.6092` |
| `probe_status` | String | `'unprobed'` | 四态：unprobed / verified / mastered / confused |
| `last_probed_at` | Long? | null | 最近探测时间（毫秒时间戳） |
| `misconceptions` | List\<String\> | `[]` | 误解注记，JSON 数组（`StringListConverters`） |
| `confidence` | Float | 0 | 置信度 0..1，仅展示用 |
| `attempts` | Int | 0 | 作答总次数（深度侧留存，不回写广度侧） |
| `correct` | Int | 0 | 判对次数（深度侧留存） |
| `streak` | Int | 0 | 当前连续判对次数，判错清零；收敛判定依赖它 |

**索引**：`probe_status`、`last_probed_at`
**为什么不建外键**：出厂命题在 assets 里，不在数据库，无法建外键；命题下架后的残留状态由
`KgClaimStateDao.deleteOrphans` 清理。

## 14. `kg_runtime_claim` 运行时命题表

对应 `KgRuntimeClaimEntity.kt`。只存**运行时才出现**的命题（云端生成 + 用户录入）。

| 列名 | 类型 | 默认值 | 说明 |
|---|---|---|---|
| `claim_id` | String | — | **主键**，由 statement 推导 |
| `statement` | String | — | 一句话可判真假的断言 |
| `expected` | Boolean | — | 标准答案：该命题是否成立 |
| `conditions` | List\<String\> | `[]` | 成立条件 / 边界，JSON 数组 |
| `explanation` | String? | null | 撞错解释 |
| `misconception` | String? | null | 撞错时暴露的误解 |
| `evidence` | String? | null | 证据原文片段，用于溯源 |
| `card_id` | String | — | 主归属卡 ID |
| `outline_path` | String | `''` | 大纲路径，广度侧派生用 |
| `source` | String | `'cloud'` | bundled / cloud / user |
| `review_status` | String | `'pending'` | pending / confirmed / rejected |
| `provider_id` | String? | null | 生成该命题的服务商标识 |
| `embedding` | ByteArray? | null | 文本向量，用于同义合并；未嵌入时退回字符级比对 |
| `created_time` | Long | — | 生成时间（毫秒时间戳） |

## 15. `kg_claim_merge` 同义合并表

对应 `KgClaimMergeEntity.kt`。解决「云端重新措辞导致 ID 漂移」。

| 列名 | 类型 | 默认值 | 说明 |
|---|---|---|---|
| `source_claim_id` | String | — | **主键**，派生出来的命题 ID |
| `target_claim_id` | String | — | 合并到的规范命题 ID |
| `similarity` | Float | 1.0 | 触发合并时的余弦相似度；manual 填 1.0 |
| `basis` | String | `'vector'` | 依据：vector / manual |
| `created_time` | Long | — | 建立时间（毫秒时间戳） |

**索引**：`target_claim_id`、`created_time`

**约定**：一条源 ID 只能指向一个目标（主键保证），避免链式映射；所有命题读写都应先过这张表
（`KgClaimRepository.resolveClaimIds`）。

知识图谱的枚举**不走 TypeConverter**：实体里存 wire 字符串，由 `KgEntityMappers` 在映射时转换。

| 枚举 | 取值（wire） | 使用表 |
|---|---|---|

列表转换器：

| 转换器 | 格式 | 使用列 |
|---|---|---|
| `ListConverters` | 英文逗号分隔 | `side_a_content_ids`、`side_b_content_ids`、`source_content_ids` |

## 维护注意

### ⚠️ 当前使用破坏性迁移

`ZhijingDatabase.getInstance` 现在带 `fallbackToDestructiveMigration()`：

```kotlin
Room.databaseBuilder(context, ZhijingDatabase::class.java, DbConstants.DATABASE_NAME)
    .fallbackToDestructiveMigration()
    .build()
```

**任何 `version` 变更在找不到对应 Migration 时会直接清空全部用户数据。** 改动前请确认：

| 场景 | 建议 |
|---|---|
| 开发阶段、数据可丢 | 可继续使用破坏性迁移 |
| 已有真实用户数据 | 必须写 `Migration(n, n+1)` 并补测试，删除 `fallbackToDestructiveMigration()` |

### 加表的常规流程

1. 新增 `entity/XxxEntity.kt`（外键列记得加索引，否则 Room 会告警）；
2. 新增 `dao/XxxDao.kt`（写操作 `suspend`，查询优先提供 `Flow`）；
3. 在 `ZhijingDatabase` 的 `entities` 与 `abstract fun xxxDao()` 中登记；
4. `version + 1`，并决定是补 Migration 还是接受清库；
5. 领域模型放 `model/`，映射放 `mapper/`，对外只经 `repository/` 暴露；
6. 同步更新本文档与 `doc/知境-数据层设计说明.md`。

### 源码编码

`data/` 下源文件统一 UTF-8，中文注释可正常显示。若在 Windows 上看到乱码，是编辑器按 GBK
打开了 UTF-8 文件，改回 UTF-8 即可，**不要重新转码保存**。
