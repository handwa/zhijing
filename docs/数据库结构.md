## 1. `content_table` 内容表

对应 `ContentEntity.kt`，说明书 3.4.1。

| 列名 | 类型 | 默认值 | 说明 |
|---|---|---|---|
| `id` | Long | 自增 | 主键 |
| `raw_text` | String | — | 原文，超过 5000 字截断（截断由数据层保证） |
| `source` | String? | null | 来源 App 包名或网址 |
| `import_time` | Long | — | 收藏时间（毫秒时间戳） |
| `analysis_json` | String? | null | 解析结果（关键词/实体/情感/主题/立场，JSON） |
| `analysis_status` | AnalysisStatus | `PENDING` | 0 待处理 / 1 处理中 / 2 完成 / 3 失败 |
| `embedding_vector` | ByteArray? | null | 512 维向量，小端 float 序列化后的 BLOB |
| `embedding_status` | EmbeddingStatus | `PENDING` | 向量是否已生成 |
| `remark` | String? | null | 用户备注 |
| `import_channel` | ImportChannel | `MANUAL` | share / whitelist / manual |

**索引**：`import_time`、`analysis_status`、`embedding_status`

**特殊实现**：重写了 `equals` / `hashCode`，对 `ByteArray` 按内容比较（便于测试与去重）。

## 2. `chunk_table` 分段表

对应 `ChunkEntity.kt`。说明书未定义，为段落级 RAG 预留。

| 列名 | 类型 | 说明 |
|---|---|---|
| `id` | Long | 主键，自增 |
| `content_id` | Long | 所属内容 |
| `chunk_index` | Int | 段序号，从 0 开始 |
| `text` | String | 段文本 |
| `start_offset` | Int | 在原文中的起始字符下标（含） |
| `end_offset` | Int | 在原文中的结束字符下标（不含） |
| `char_count` | Int | 段文本字符数 |

**外键**：`content_id` → `content_table.id`，`CASCADE`
**索引**：`content_id`、`(content_id, chunk_index)` **唯一**

---

## 3. `vector_table` 向量表

对应 `VectorEntity.kt`。说明书未定义，用于统一承载 512 维向量。

| 列名 | 类型 | 说明 |
|---|---|---|
| `id` | Long | 主键，自增 |
| `owner_type` | VectorOwnerType | `content` 或 `chunk` |
| `owner_id` | Long | 对应 `content_table.id` 或 `chunk_table.id` |
| `dim` | Int | 维度，当前恒为 512 |
| `vector` | ByteArray | 小端 float 序列化后的向量 |
| `model_id` | String | 产出该向量的嵌入模型标识 |
| `created_time` | Long | 写入时间（毫秒时间戳） |

**索引**：`(owner_type, owner_id)` **唯一**、`owner_type`

**注意事项**：
- `vector_table` 是向量的**唯一真源**，内容级与分段级向量都放这里
- 写入内容级向量时，在同一事务内同步刷新 `content_table.embedding_vector`
- owner 是多态的，**无法建外键**，级联清理由 Repository 显式完成
- `model_id` 用于换嵌入模型后判定旧向量是否失效

## 8. `qa_record_table` 问答记录表

对应 `QaRecordEntity.kt`，说明书 3.4.6。

| 列名 | 类型 | 默认值 | 说明 |
|---|---|---|---|
| `id` | Long | 自增 | 主键 |
| `question_text` | String | — | 用户的问题 |
| `answer_text` | String? | null | 生成的回答 |
| `source_content_ids` | List\<Long\> | 空 | 回答引用的内容 ID，用于溯源 |
| `retrieval_ms` | Long | 0 | 检索耗时（毫秒） |

**索引**：`answer_status`

**现有查询**：
```kotlin
@Query("SELECT * FROM qa_record_table ORDER BY id DESC LIMIT :limit")
fun observeRecent(limit: Int): Flow<List<QaRecordEntity>>
```

**⚠️ 重要限制**：该表**没有 `conversation_id`、没有 `seq`、没有 `token_count`**，因此：

- 不能作为多会话的归档区
- 不能可靠地按会话顺序回放
- 不能用于计算 token 预算

## 表关系图

```
content_table (核心表)
   ├─1:N─ chunk_table       [CASCADE]
   ├─1:N─ parse_task_table  [CASCADE]
   ├─1:N─ association_table [CASCADE ×2]
   └─1:N─ vector_table      [多态，Repository 手工清理]
                            ↑ owner_type = "content"

topic_table （自引用 parent_tag 构成树）
     └─ 被 stance_compare_table.topic_tag 弱引用（无外键）

qa_record_table   ─ 独立，无外键
wake_plan_table   ─ 独立，无外键
pet_status_table  ─ 独立单例
```

## 数据访问层

所有 Repository 通过 `ZhiJingData` 暴露：

```kotlin
val data = ZhiJingData.get(context)

data.contents        // 收藏内容、分段与向量
data.associations    // 关联卡片
data.topics          // 主题树
data.stanceCompares  // 观点对照
data.wakePlans       // 记忆唤醒
data.qaRecords       // 问答记录
data.petStatus       // 养成系动物
data.parseTasks      // 解析队列
```

**架构约束**：`ZhijingDatabase`、Entity、DAO 全部是 `internal`，模块外只能通过 Repository 访问。

## 与「上下文功能」的差距

| 需要的存储 | 现有表能否复用 | 结论 |
|---|---|---|
| 归档区（全量消息） | `qa_record_table` ❌ | 需新建 `message_table` |
| 会话快照 | 无 | 需新建 `conversation_table` |
| 工作记忆 | — | 内存 `List<Turn>`，无需建表 |

`qa_record_table` 不适用的原因：

1. 无 `conversation_id` —— 无法做多会话
2. 无 `seq` —— 顺序不可靠
3. 无 `token_count` —— 算不了 token 预算

**新增两表后：表数 10 → 12，`version` 需从 `1` 升到 `2`。**

## 增量变更注意

`ZhijingDatabase.kt:38-39` 注释说明当前阶段不引入迁移：

```kotlin
// `exportSchema = false`：本阶段不引入数据库迁移，先不落地 schema 目录；
// 后续加 Migration 时再打开并配置 `room.schemaLocation`。
```

添加新表时可选：

| 方案 | 适用场景 | 数据影响 |
|---|---|---|
| `fallbackToDestructiveMigration()` | 开发阶段 | **会清空已有数据** |
| 编写 `Migration(1, 2)` | 已上线 | 保留数据 |

## 附带说明

`data/` 目录下源文件中的中文注释在 UTF-8 下显示为乱码（如 `璇存槑涔?3.4.1` 实为「说明书 3.4.1」），源文件应为 GBK 编码保存。
